## Decisions worth keeping

**Trusted Publishing (OIDC), not API tokens.** The whole publish path is
keyless: GitHub Actions mints a short-lived OIDC token (via `id-token: write`),
and PyPI verifies its claims against the registered trusted publisher before
accepting the upload — no secret is stored or rotated. This was a deliberate
call: managing PyPI API tokens alongside the existing SSH-based git auth was
judged too error-prone.

**`github.sw` is an SSH-config alias for github.com, not a GitHub Enterprise
host.** An early assumption that the internal-looking origin was GHE Server led
to a wrong belief that OIDC couldn't reach these runners (and a phantom "mirror"
requirement). The origin is `Host github.sw → HostName github.com` selecting a
specific key; Actions run on github.com and PyPI's OIDC trusts them directly.
Worth stating in the docs because the origin URL misleads.

**Reusable workflows cannot do Trusted Publishing — so build+publish live in one
workflow.** The first automated design (#53) had `release.yml` call `wheels.yml`
via `workflow_call`. It cut v5.7.2's tag and GitHub Release correctly but the
upload **403'd**: PyPI Trusted Publishing does not support reusable workflows
(the OIDC `workflow` claim is ambiguous), documented at
<https://docs.pypi.org/trusted-publishers/troubleshooting/#reusable-workflows-on-github>.
The other half of the trap: a GitHub Release created by CI's `GITHUB_TOKEN` does
**not** trigger another workflow (anti-recursion), so a separate publish workflow
would never fire on an automated release either. #57 resolves both by
consolidating everything into `wheels.yml` as native jobs — `push: main` runs
semantic-release then builds+publishes in the same run; `release: published` and
`workflow_dispatch` remain for manual and dry-run. One direct workflow, one
trusted publisher, no token.

**The first release has to be bootstrapped by hand.** semantic-release computes
the next version from the last tag, and there was none — so every prior "Release"
run was a silent no-op. v5.7.0 was created manually (`gh release create`), which
established the baseline tag; from 5.7.1 on, the machinery had something to count
from.

**Detect a stale compiled extension by symbol presence, not version.** A user hit
`cannot import name 'tensor' from 'mtl5._core'` — an editable install serving
updated `.py` against a `_core` built before the tensor submodule existed. A
version-string check would not catch it: in an editable install the metadata and
`_core` versions both stay at the old build while only the source advances. The
guard (#54) checks that the major `_core` submodules are present and, if not,
prints what is missing plus the rebuild command.

**The README is the PyPI long description, and PyPI bakes it per-version.** The
5.7.0 project page told users to `pip install .` (a source-only command) because
the README predated the PyPI channel and the pre-flight check only verified it
*rendered*, not that it was *correct for a PyPI reader*. Fixed in 5.7.1 — but the
corrected page only appears on a new upload, since PyPI does not allow editing a
published version's metadata.

**64-bit only.** cibuildwheel's default `auto` archs still include the 32-bit
`win32` target on Windows; a C++20 / nanobind / Highway extension has no 32-bit
toolchain, so `auto64` is required (#49).

## Loose end

The automated **`released=true`** path — a `feat:`/`fix:` merge that
semantic-release turns into a version bump, build, and publish in one run — has
been validated by reasoning and by its no-op branch (a `ci:` merge correctly
skips build/publish), but has not yet done a real production upload. That first
happens on the next feature/fix merge and is worth watching.
