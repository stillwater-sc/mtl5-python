## Decisions worth keeping

### Integer GEMM (#96)

- **`mixed.matmul` is overloaded on the integer dtypes, not given a new name.**
  `accumulator="i32"` is required, as it already is for `mixed.dot` on these
  dtypes, and the result is the accumulator type.
- **The quad kernel is chosen by name, `mixed.matmul_quad`, not by a heuristic.**
  It runs MTL5's `mult_quad` (VNNI / SDOT) micro-kernel. It refuses `i8 × u8`:
  a GEMM is not symmetric, so the pair cannot be swapped onto `u8 × i8` the way
  a dot product can.
- **`u8 × u8` gives uint32, so `DenseMatrix_u32` exists**, as storage only.
- **`quad_dot` has three states (`none` / `partial` / `all`), not a flag.**
  x86 and ARM implement opposite pairings first, so `partial` is the common
  answer and a boolean would mislabel one pairing. `quad_dot_native` gives the
  per-pairing answer.
- **The test that the right kernel ran is behavioural**, an asymmetry between
  the two entry points, with no private hook into the dispatch.

### `universal_dtypes` interop (#14)

- **Copy the bits; don't share the buffer.** The two packages may be built on
  different Universal releases, and what releases agree on is the encoding, not
  the C++ object layout. MTL5's Universal containers also own their storage. The
  copy is one pass, which is nothing next to emulated arithmetic.
- **`.to_universal()` is new, and `to_numpy()` is unchanged.** `to_numpy()`
  keeps meaning "widen to float64".
- **Formats are matched by name, so the tests check meaning, not just bits.**
  Both libraries decode every 8- and 16-bit pattern, 50,000 random patterns per
  wider type, the posit64 value just above 1.0 (which float64 cannot hold) and
  cascades with non-zero low limbs, and must agree.
- **Same name, different format: `fp8e5m2` is refused.** MTL5's `fp8` is
  `cfloat<8,2>` (e2m5): 200 of the 248 finite values differ. Copying the bits
  across would succeed silently and mean something else.
- **The name comes from `dtype.type.__name__`.** `dtype.name` is the DType class
  spelling, e.g. `Posit16DType16`.

### Universal v5.11.0 in `universal_dtypes` (universal_dtypes#72)

The pin had been on v4.7.9 since August. The bump turned four tripwire tests red
on purpose. `universal_dtypes`' RELEASING procedure says to re-grade the docs and
invert the tests in that case, not revert, and issue #65 was the checklist for
it.

- **takum64 arithmetic is now full width** (universal#1300). It had been
  evaluated in double, so even `x + 0` lost bits. The round trip through
  dd/td/qd is now exact.
- **takum32 had been double-rounded**, which #65 did not anticipate and the docs
  had wrongly called exact. Through double, `0x44000001 * 0x40000001` gave
  `0x44000002`; the correctly rounded result is `0x44000003` (universal#1616).
  Upstream's rule is that rounding through double is harmless only for
  significands up to 25 bits.
- **Signaling NaNs now stay NaN** when narrowed into `fp16` / `fp8e5m2`
  (universal#1303). The two strict xfails began passing and their markers came
  off.
- **The fix stops at the math ufuncs.** They belong to `universal_dtypes`, not
  to Universal, and still compute in double, so takum64 `sqrt`/`exp` stay
  limited to double. A test pins that boundary.
- **It is a `fix`, not a chore**, because numerics change. That made the
  release 2.5.1.
- **The new tests discriminate:** 5 of them fail against the published v4.7.9
  wheel.

### Universal v5.11.0 here (#112) was inert, and measured to be

Every header that changed between v5.10.0 and v5.11.0 is efloat or lindex,
neither of which this package binds. That was confirmed, not assumed: 750
results (conversion, `norm`, `dot`, `matmul` and `solve`, 10 trials on each of
the 15 Universal dtypes) are bit-identical to a v5.10.0 build with gcc and
clang. Review pointed out that "both packages on one Universal" holds only for
builds that fetch it. A found installation (≥ 5.8.0) overrides the pin, which is
safe because the interop relies on encodings, not matching versions. The
rationale comment in `mtl5_module.cpp` now says so instead of naming a version
pairing.

### PyTorch (#15, #110)

`__torch_dispatch__` wrapper subclasses have matured as a *storage format* that
decodes on use (torchao's NF4, int4 and MX formats), and autograd and
`torch.compile` see ordinary float operations. PyTorch still cannot register a
new dtype. #15 is rescoped accordingly:
- posit weights decoded to float32/bfloat16 when a layer uses them;
- optionally, a forward-only CPU `F.linear` that accumulates in a quire, for
  accuracy studies.
