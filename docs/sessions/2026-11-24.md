## Decisions worth keeping

- **Factors come back as copies, in MTL5's permutation convention.** The
  properties `L`, `U`, `R`, `row_perm`, `col_perm` and `perm` return
  `SparseMatrix_*` and int64 copies, so they outlive a later `refactor()`. The
  convention is `p[new] = old`, giving `A[row_perm][:, col_perm] == L @ U`.
  That is the inverse of SciPy's `perm_r`/`perm_c`, which is why the names
  differ; the SciPy page shows that `argsort` converts one into the other.
- **Exposing the factors exposed a race.** A getter on one thread could read
  a factor while `refactor()` on another rewrote it. Each factor object now
  holds a `std::shared_mutex`: getters, `solve` and `iterative_refine` read
  under a shared lock, and `refactor` writes under an exclusive one, taken
  after the GIL is released. A subprocess test with a barrier reproduces the
  race without the lock.
- **Every docs page is executed, and asserts what its prose says.** The
  Sphinx build runs with `nb_execution_mode="force"` and `-W`, so a fill
  regression or a stale claim fails the docs build. The assertions check
  deterministic quantities only (fill counts, residuals, exponents); timings
  are printed, never asserted, after one wall-clock assert proved flaky.
- **nanobind needs adapting for autodoc.** Sphinx 9 ignored a custom
  documenter, so `docs/conf.py` wraps nanobind functions in the Sphinx process
  instead, moves overload signatures to the end of the docstring, and applies
  NumPy-style section parsing to callables only, because it mangles property
  docstrings that contain colons.
- **Pages deploys only from `main`, and only the latest commit.** The
  workflow skips the deploy if `main` has moved on since the build started,
  so a slow build cannot overwrite a newer site.
- **A local CodeRabbit pass before each push** (`coderabbit review --agent
  --committed --base main`), at the user's request, so that CI and the server
  review run on code that has already been through one round.

- **An upstream bug found by the docs is fixed upstream first.** Measuring
  `threshold` for the diagnostics page showed it was nearly inert under every
  ordering but `natural`. MTL5's LU preferred row `k` as the diagonal of
  column `k` of `A(:, q)`, whose diagonal is row `q[k]`. Rather than document
  the bug and a workaround, it was filed as MTL5 issue 916, fixed in #917,
  released as 5.24.1 the same day, and pinned here by #133. The page was then
  written against the fixed behaviour.

- **mtl5-python's MAJOR.MINOR tracks MTL5's; everything else is a patch.**
  semantic-release counts a `feat` as a patch (`minor_tags = []`), so #135
  and #137 shipped as 5.24.2 and 5.24.4. A minor bump to follow MTL5 is
  manual: the pin-bump PR sets `pyproject.toml` and is committed as
  `chore(deps)`, as #122 was, because a `feat` would make semantic-release
  compute the next patch from the last tag. Then v5.x.0 is tagged on its
  merge commit, and semantic-release resumes from that tag.
- **KLU's factors are exposed as its structure, not as an invented (L, U).**
  KLU factors only the diagonal blocks of B = P(RA)Q. A global L and U would
  need fill-producing terms like Lᵢ⁻¹Bᵢⱼ. So `ms.klu` returns `B`, the BTF
  permutations, the block boundaries, the row scaling, and `block(i)` with
  each block's own factors.
- **Nested dissection was measured before it was accepted.** The issue as
  first written asked for ND fill below AMD from 64×64 up. A hand-built
  geometric ND in Python missed that at every size up to 512×512. So the
  implementing agent was told to measure first, and to assert only what holds
  with margin. The merged ordering beats AMD from about 128×128 up (0.92×,
  0.84× at 256×256, 0.78× at 512×512, and 0.64× on a 32³ grid). Its tests
  assert those large sizes and the growth exponents, not 64×64.

## Notes

- **Mixed precision buys memory, not time, on this CPU.** A float32 sparse
  factorization takes about as long as a float64 one, because the time goes
  to index handling and scattered access. The page says so, and lists where
  it does pay: memory, bandwidth, and hardware with fast narrow arithmetic.
- **A converged refinement is not as accurate as a float64 direct solve.**
  It drives the residual to the float64 level, and its forward error stays
  within κ times the achieved relative residual (in consistent norms). That
  bound is all a small residual guarantees: at κ ≈ 8e5 the refined error was
  about 500× the direct solve's. Refinement stalls at κ ≈ 1e8, where GMRES preconditioned
  by the same float32 factor still converges.

- **What the factor objects do not tell you.** A singular float64 matrix,
  the Neumann Laplacian, factors without raising: its last pivot is rounding
  noise (pivot ratio 1.4e-15), not zero, and `solve` returns entries of size
  1e16. `num_perturbed` stays 0. A small `pivot_perturb` (1e-10) turns it
  into a detector, and the diagnostics page recommends checking the pivot
  ratio from `ms.to_scipy(F.U).diagonal()`. The repr shows neither `num_perturbed` nor the
  accumulator, and `SupernodalLDLT`'s repr shows only `n`.
- **The accumulator helps only where update chains cancel.** On the badly
  scaled n = 400 test matrix (cond ≈ 2.8e10), a float64 accumulator improves
  the float32 direct error 1.3–2.5× and the refined error 6–300×. On a
  well-scaled Poisson problem it makes no difference, or is slightly worse.
- **Another session's builds run at `-j12` on this machine.** Two of today's
  MTL5 builds overlapped one. Check for `cmake`/`ninja`/`make` by exact
  process name (`pgrep -x`), since `pgrep -f "cmake --build"` also matches
  the shell running the check.
- `west0479` is vendored in `notebooks/data/` from NIST Matrix Market, with
  its SHA-256 recorded in `notebooks/data/README.md`. Its LU fill under
  `colamd` differs from MATLAB's 5920, because the pivoting differs; the
  notebook says so.
- The SPD page shows that the natural ordering's Cholesky fill of
  `poisson2d` equals the envelope of A exactly. That makes a fill count you can
  check by hand, and the page asserts it.
- Local CodeRabbit passes and server reviews draw on the same allowance of
  about 4–5 reviews per rolling hour. Several local passes in a row left the
  server review rate limited more than once.
- scikit-learn 1.7.0 in the `p311` venv failed a diagonal check; upgrading to
  1.9.1 fixed it.

### Afternoon: diagnostics, two upstream changes, and three features

- **The docs found an upstream bug.** Measuring `threshold` for the
  diagnostics page showed it was nearly inert under every ordering but
  `natural`. Column k of A(:, q) has its diagonal in row q[k], and MTL5
  checked row k. It was filed as MTL5 issue 916, fixed in #917 with a
  regression test that fails on the old code, released as 5.24.1 the same day,
  and pinned here by #133. On a 900-row weak-diagonal grid under AMD,
  `threshold=0.01` went from 64,118 nonzeros to 21,907.
- **CodeRabbit kept finding overstatements in prose about numerics.**
  Across #134 and #136 there were about twenty findings, all valid and all
  fixed. They were claims made stronger than the evidence:
  - κ·u < 1 presented as necessary rather than sufficient;
  - a small pivot ratio presented as proof of singularity;
  - the L containment in George–Ng, which was never checked;
  - symbolic and numerical fill conflated;
  - fill said to be confined to the separator block;
  - values said to only ever increase LU fill.

  Worth remembering when writing about numerics: say what was measured.
- **Two release jobs raced.** #136 merged while #137's semantic-release job
  was running. The job refused to push onto a moved `main` and failed, and
  the next run released 5.24.4 with #137 in it. Space merges a few minutes
  apart when each would cut a release.
- **The ASCII banners in a build log are MTL5's CMake configure step**
  (`tools/cmake/banners.cmake`). The editable install rebuilds the first time
  a process imports mtl5 after a source change, so they can appear in a
  Sphinx log or a script's output. They never reach a rendered page.
- **CodeRabbit spending.** The included review allowance ran out repeatedly,
  and the user's rule became: pay for an on-demand PR review (at most $2)
