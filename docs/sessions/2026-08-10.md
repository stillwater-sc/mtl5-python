# Session — 2026-08-10

One question — *"how do we release the Python binding backed by MTL5 v5.8.0?"* —
whose answer turned out to be **you can't**, and which surfaced three defects on
the way to shipping **`mtl5` 5.9.0**: the first release of this package that is
actually reproducible.

## Shipped

| PR / issue | |
|---|---|
| #61 | pin MTL5 → `v5.9.0` and Universal → `v4.7.9`; bump to 5.9.0; apply the floor to `find_package` too |
| #62 | issue: the accumulator tests rank against a float64 reference |
| #63 | fix those tests to rank against an exact (`math.fsum`) reference |

**`mtl5 5.9.0` is live on PyPI**, built from tag `v5.9.0` at commit `cd75870`,
9 wheels (Linux/macOS/Windows × cp310–312) plus sdist, published keylessly via
OIDC. Install-verified from a clean venv.

## The answer to the actual question: not v5.8.0

The ask was a v5.8.0-backed release. Building against a v5.8.0 checkout gives
**141 errors in two files**, all from APIs that landed after v5.8.0:

| file | errors | missing in v5.8.0 |
|---|---|---|
| `mtl5_mixed_precision.cpp` | 116 | `two_norm<Accumulator, Result>` / `frobenius_norm<Accumulator, Result>` — v5.8.0's signature is `template <typename Accumulator = void, Vector V>`, no `Result`, so `<Acc, double>` binds `double` to `V` and fails the `Vector` constraint |
| `mtl5_complex.cpp` | 5 | `cholesky_h_factor`, `cholesky_h_solve`, `ldlt_h_factor`, `ldlt_h_solve`, `CHOLESKY_NOT_HERMITIAN` |

Backing v5.8.0 would have meant deleting mixed-precision accumulator norms and
complex Hermitian factorizations — a regression against what 5.7.2 already
shipped. v5.9.0 has both and builds clean, so the release tracks v5.9.0.

Worth stating plainly because it is a standing constraint, not a one-off:
**v5.9.0 is the floor for this binding surface.**

## Decisions worth keeping

**The dependency was never pinned at all.** `CMakeLists.txt` fetched both MTL5
and Universal from `main`. FetchContent runs at `pip install` time, so every
wheel CI shipped and every from-source install was built against whatever those
branches happened to be at that moment — **5.7.0 through 5.7.2 are not
reproducible**, and nothing about them records which MTL5 they contain. The pin
is now the thing that gives a released wheel a meaning, and bumping it is what a
minor release of this package *is*.

**Release tags, not commit SHAs.** Raised in review and declined. `GIT_SHALLOW`
and SHA pins are mutually exclusive in CMake, so SHAs would cost a full clone of
Universal (3287 files plus complete history) on every `pip install` and every
wheel build across 3 OS × 3 Python in cibuildwheel. What they buy is protection
against someone in our own org force-moving a tag on our own repository. They
would also destroy a checkable invariant: `GIT_TAG v5.9.0` sitting next to
`version = "5.9.0"` *is* the version policy made legible; a SHA is not.

**A pin that governs only one build path is not a pin.** The original commit
pinned the fetch but left `find_package(MTL5 QUIET)` bare — and when that
succeeds it skips the FetchContent block entirely. Anyone with MTL5 5.7.x
installed system-wide would have built against it and hit the same ~140
`norms.hpp` template errors, with nothing pointing at the cause. Both lookups
are now version-floored. `COMPATIBILITY SameMajorVersion` (which both projects
generate) was verified rather than assumed: against a requested 5.9.0 it rejects
an installed 5.7.0, accepts 5.9.0 and 5.10.0, and rejects 6.x — and the 6.x
rejection is right, since an MTL5 major bump is the manual-intervention case in
the version policy.

**semantic-release reads the current version from the last git tag, not from
`pyproject.toml`.** It only ever *writes* that file. So a minor/major bump must
not ride a release-worthy commit: merging a hand-set `version = "5.9.0"`
alongside a `feat:`/`fix:`/`perf:`/`refactor:` commit makes the `release` job
compute 5.7.2 → **5.7.3** from the tag and rewrite the 5.9.0 back down. The bump
was landed under `build:` (not in `patch_tags`) so the job no-ops, then tagged by
hand. Confirmed in production: the merge produced `No release will be made,
5.7.2 has already been released!` with every publish job skipped. Now documented
in `docs/pypi-release.md` §5 and §6.

**`gh release create` needs `--target`.** When the tag does not already exist,
`gh` creates it from the tip of the default branch *at that moment* — so an
unrelated merge landing between the CI check and the release command is what
gets tagged and published. v5.9.0 was cut with `--target cd758705`, the exact
commit CI went green on.

**A test that scores accuracy against float64 cannot rank anything better than
float64.** `test_wider_accumulator_is_monotonically_better` asserted
`quire <= f64` while computing its reference with `np.dot` — itself a sequential
float64 accumulation carrying rounding error. So the `f64` accumulator
reproduced the reference bit for bit and scored a perfect `0.0`, while the exact
quire differed by `1.14e-16` and scored *worse*. The test penalised the quire
for being right. It was not a flake: it fails whenever the f64 accumulator
matches numpy's summation order, which is the ordinary case, and CI stayed green
only because FP contraction on those runners perturbed one of the two.

`math.fsum` is correctly rounded regardless of summation order, and the quire
reproduces it exactly — verified bit-for-bit for both `dot` and `two_norm`. With
a true reference the tests can assert the actual property instead of a
tolerance: `== exact` rather than `rel=1e-15`, and `quire == 0.0` rather than
`quire <= f64`. **The old tolerance was hiding the very claim the suite existed
to make** — `test_quire_is_exact_for_posit` never actually tested exactness,
because `rel=1e-15` absorbed the discrepancy.

**`np.longdouble` is not a portable high-precision reference.** It is 80-bit
only on x86 Linux, and plain float64 on Windows and macOS/arm64.
`test_a_wider_accumulator_is_strictly_better` used it and asserted
`err["quire"] == 0.0`, so on two of the three CI platforms that assertion was
already being made against a float64 reference and passing on luck. Same
`math.fsum` fix.

**Commit type is a release decision, not a formatting one.** The test fix was
first written as `fix:` — which is in `patch_tags`, so merging it would have
auto-cut **v5.9.1** and published a wheel to PyPI for a change that alters no
shipped code. Retyped `test:`. Verified after merge: `No release will be made,
5.9.0 has already been released!`, no stray tag.

## Notes

`import mtl5` from the repository root fails with `ModuleNotFoundError: No
module named 'mtl5._core'` even when the wheel is correctly installed — the
source `mtl5/` directory shadows the installed package. This is the #54 guard
working as designed and its message says exactly that, but it will greet anyone
verifying a published wheel from a checkout. Run from another directory.

The v5.9.0 release notes on GitHub and the `[5.9.0]` CHANGELOG section carry the
same content; the CHANGELOG section was written before the `find_package` floor
landed in review and was backfilled afterwards to match what actually shipped.

## Loose end

Still unexercised: the fully automated `released=true` path — a `feat:`/`fix:`
merge that semantic-release turns into a bump, build, and publish in one run.
Every release so far — 5.7.0, 5.7.1, 5.7.2, and now 5.9.0 — has been cut by hand
via `gh release create`, and the automated path has only ever been observed taking
its no-op branch — correctly, and now twice in production, but never the branch
that actually uploads. It carries over from the 08-07 session, and the next
`feat:`/`fix:` merge to `main` is when it finally runs for real. Watch it.
