## Decisions worth keeping

**Type-erase the preconditioner rather than instantiate the cross product.**
MTL5's 10 Krylov solvers each take the preconditioner as a template parameter,
so binding every pairing would have been 10 × 8 × 2 dtypes = 160 instantiations
of a full iterative solver. A virtual `apply`/`apply_adjoint` behind a value
adapter satisfying MTL5's `M.solve` contract brings that to 20, and the virtual
call is nothing next to a sparse triangular solve. It also absorbed an upstream
inconsistency that would otherwise have surfaced in Python: `identity`,
`diagonal`, `ssor` and `block_diagonal` are templated on the matrix type,
`ilu_0`, `ic_0`, `ilut` and `ildl` on the value type.

**The gap analysis called for that refactor *before* expanding from 3×2 to
10×8, and the ordering is what paid.** Doing the compatibility sweep first —
all 10 solvers against 5 preconditioners, against known solutions — is what
surfaced [mtl5#392](https://github.com/stillwater-sc/mtl5/issues/392), where
`bicg` computed `rho` from `z̃ᵀz` instead of `zᵀr̃` and therefore worked only
with the identity preconditioner. Bound first and tested after, that would have
shipped silently wrong with every preconditioner but one.

**Build what upstream lacks when the alternative is unusable.** `multigrid`'s
constructor asks for coarse operators, and the obvious way to form them —
`R * A * P` — goes through `operator*` on two `compressed2D`, which returns a
**dense** matrix. At fine-grid size that is precisely the intermediate a
hierarchy cannot afford, so `mtl5.mg.galerkin` forms the triple product
sparsely. Similarly `multigrid_1d` builds a consistent hierarchy rather than
handing the caller five interlocking pieces.

**Materialise the views.** Upstream each holds a `const Matrix&`, which is the
same lifetime hazard that segfaulted `pc::ssor` through its standalone solve
path — a Python caller passing a NumPy array or converted scipy matrix hands
over a temporary the view would outlive. The laziness buys nothing here either,
since there is no expression template to feed.

**Enumerate a compile-time interface when the space is small; reimplement when
it is not.** `mtl::array::slice` derives its result rank from argument *types*,
giving 3^N combinations per rank — reimplementing was the only option. Tensor
`contract` takes index names as `char` template parameters, but the repeated
index sits in one of two positions on each side, so four instantiations cover
every rank-2 contraction up to relabelling. Python reaches MTL5's own kernel
there. **Checking which of those two situations you are in is the first question
for the next compile-time interface.**

## Where the risk moved, and what the tests assert

Enumerating `contract` means the kernels are correct and the *dispatch* is what
could pick the wrong one of four. So each pattern is checked against a NumPy
reference distinct from the other three — plus a test asserting those four
references are pairwise different, since a symmetric fixture would have made the
whole parametrisation vacuous.

The multigrid tests assert **mesh independence**, not that the residual fell. A
mis-scaled coarse-grid correction still converges, just at roughly the
smoother's rate; a test checking only "residual decreased" would have passed
while the coarse-grid correction did nothing.

## Self-corrections

Four surprising results today were mine, not upstream's. Each would have become
a false bug report if the first output had been trusted:

- A V-cycle measured at 0.775 per cycle looked like poor multigrid performance.
  It was my coarse operator — a fresh Poisson instead of R·A·P, which
  mis-scales the correction. With the Galerkin product it is 0.03.
- `banded_view(A, -1, 1)` returned only the superdiagonal. The parameters are
  bandwidths, not signed diagonal offsets.
- `hermitian_view` did not return the adjoint. It never claimed to — it
  reconstructs a Hermitian matrix from the upper triangle.
- A test fixture I wrote as "Hermitian" was not, and the view was right.

Two of those became guards that make the binding safer than the raw API:
`banded` refuses a negative bandwidth, `hermitian` a non-real diagonal.

  upstream would let that guard become a dispatch — the same shape as the

  [mtl5#401](https://github.com/stillwater-sc/mtl5/issues/401) as an observation

- MTL5's `jacobi` has no damping parameter, so it cannot express the damped
  Jacobi (ω ≈ 2/3) that multigrid actually wants as a smoother.
