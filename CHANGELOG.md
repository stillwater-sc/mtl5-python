# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

Release sections below the marker are generated by python-semantic-release from
conventional commits; the `Unreleased` section above it is maintained by hand,
because a list of commit subjects does not say *why* a binding refuses input it
could have accepted. Both are kept.

Versioning: the **minor** component tracks the MTL5 release this is built
against, and semantic-release manages only the **patch** component.

- **Trends in `mtl5.bench`** (#121, milestone P5).
  - **Only comparable runs:** `analyze.trend` reads one entry's history on
    one machine, at one label and thread count, from the `trend_results`
    view only, so every row is a complete run whose check passed.
  - **Series and breaks:** runs are grouped into series by their
    comparability key, and into points by commit. Where the key changes
    along the history (a compiler upgrade, a new machine state), that is a
    series break: it is marked with the fields that changed, and nothing is
    compared across it.
  - **Confidence intervals:** 95%, from run-to-run noise on a log scale,
    pooled over a series' repeated sessions. Without repeats, the noise
    comes from successive points instead, and the summary says which.
  - **Change points:** binary segmentation within each series. A step is
    flagged when it is at least `k` standard errors of the measured noise
    (default 4) and at least `min_effect` in size (default 2%). It is a
    regression or an improvement by the metric's direction. With 5% noise,
    10 commits and 3 runs per commit, pure noise raised a false change point
    in at most 2 of 100 synthetic series, a 2% step was flagged in at most
    10, and a 20% step in all 100.
  - **Figure** (`plot.trend`): every run as a faint dot, each commit's mean
    with its interval, level lines between change points, series breaks
    dashed and labelled, change points coloured and labelled with the step.
  - **CLI:** `mtl5-bench trend ENTRY --machine M` prints a summary and the
    change points and draws the figure. `--fail-on-regression` exits 3 when
    a regression is found.
  - **Entry names:** an entry can be named without its area everywhere:
    `gemm/f64` matches `blas3/gemm/f64/...`.
  - On MTL5's data, histories are 1 to 3 commits with two sessions each.
    The Ventuno Q's `native-fast` history has a real series break at
    `bf315e4` (`build_config`), and no change points are found.

- **Cross-machine analysis in `mtl5.bench`** (#121, milestone P4).
  - **Which runs a machine contributes:** each machine's comparable runs,
    its latest commit's sessions at one thread count. The default is the
    most threads the machine has a run of (`threads="max"`). MTL5 takes two
    sessions per commit, so most machines contribute two runs, and every
    number comes with its spread.
  - **Analyses:** `analyze.machines` (CPU, build, probes and the f64 ridge
    point per run) and `analyze.cross_machine` (chosen entries by
    `gflops`, `roofline_pct`, `gbytes_per_s` or `median_s`). Both keep only
    runs with a recorded commit and a clean tree.
  - **Tables** (`mtl5.bench.tables`): a machine table and an entries ×
    machines comparison, each the median of a machine's runs. They are
    written as Markdown, with the provenance line, or as CSV.
  - **Figures:**
    - machine balance: FMA peak against bandwidth, with constant-intensity
      diagonals;
    - a cross-machine dot plot with min–max bars across sessions. Results
      MTL5 flagged as cache-resident or with a suspect work model are
      hollow, which is why some sit above 100% of the roofline.
  - **CLI:** `mtl5-bench table {machines,compare}` and
    `mtl5-bench figure {balance,compare}`. `--threads` also takes `max`,
    and `--machines` selects machines.
  - Numbers in figures and tables are no longer written with an exponent
    when large: 1202, not `1.2e+03`.

- **Benchmark figures in `mtl5.bench`** (#121, milestone P3).
  - Four core figures:
    - a capability card: CPU, build, FMA peaks, bandwidths and the roofline
      they make;
    - a roofline with every entry of a run placed on it;
    - speedup against threads;
    - a rate against problem size, from the `bench_all` sweeps.
  - **Two steps.** `mtl5.bench.analyze` returns a DataFrame per question,
    and `mtl5.bench.plot` draws a figure from that frame and nothing else.
    `BenchFigure.save` writes PDF, SVG, PNG and the frame as CSV, and
    `plot.from_csv` redraws the same files, byte for byte, from the CSV. The
    tests compare data, not pixels: the analysis reproduces pinned frames,
    each figure's artists hold the frame's numbers, and redraws are
    byte-identical.
  - **House style** (`mtl5.bench.style`):
    - colour: Okabe-Ito without its yellow;
    - grayscale: a marker and a dash pattern per series;
    - column- and page-width sizes;
    - TrueType text in the PDFs;
    - no timestamps in the files.
  - **Provenance footer** on every figure: machines, commits, runs and dates,
    plus `INCOMPLETE PROVENANCE` when a run has gaps.
  - **Run selection.** Incomplete runs are read only on request
    (`tiers=`, or `--include-incomplete`).
  - **Thread scaling** compares the latest multi-threaded run with a 1-thread
    run of the same problem class, backend (BLAS vendor included), commit,
    build and machine state. Only runs with a recorded commit and a clean tree qualify. Pinning
    is left out of the state: a 1- and an 8-thread run differ in their CPUs
    by design.
  - **Dirty trees:** the stored `git_dirty` is set when either the build
    (`git_dirty`) or the preflight's checkout (`tree_git_dirty`) was dirty,
    as the tier rule already was. The schema moves to version 3, so a
    version 2 database asks to be rebuilt.
  - **Rate against size** draws one line per run. Rows of one point that
    differ in a column the format does not model are refused, not averaged.
  - **Layout.** The layout is fixed once when a figure is built. Left to
    constrained layout, writing a PNG before an SVG moved the SVG's axes.
  - **CLI:** `mtl5-bench figure {card,roofline,scaling,rate}`. The `bench`
    extra now includes matplotlib.

- **Legacy benchmark formats in `mtl5.bench`** (#121, milestone P2).
  - MTL5's CSV harnesses and `bench_blas.py --json` are ingested alongside
    `mtl5_bench`. Each dialect is a declarative `Format` in
    `mtl5.bench.formats`: its signature columns, parameters, metrics with
    units, repeat column, status gates and sidecar exemptions. Formats are
    matched by header, not file name, and a header no format matches is
    `deferred` with the header in the reason.
  - Values go to a long `measurements` table (one row per file row and
    metric, parameters as JSON) and a `trend_measurements` view.
  - A file outside a timestamp directory takes its run time from the git
    commit that added it (`time_source = 'git'`); renames count as adds.
    Committing a file later re-evaluates it.
  - The shell harnesses' sidecar spellings (`host`, `cpu`, `commit`) are
    read as aliases, and `.sidecar-exempt` marks grandfathered files.
  - **On MTL5's tree at `20feb69`:** all 164 CSVs match a format, with
    none deferred or rejected, giving 53,116 measurements. Only the 22
    interleave runs reach the complete tier (5,544 measurements, 924 series).
    The other CSV harnesses never recorded `clock_policy` and `bench_cpus`,
    or lack a sidecar, so their runs are ingested but kept out of trends.
    The 8 n_c model sweeps hold predictions only and are `ignored`.
  - The database schema moves to version 2 (`measurements`, `time_source`);
    a version 1 database asks to be rebuilt.

- **Benchmark data ingestion: `mtl5.bench` and `mtl5-bench ingest`** (#121,
  milestone P1).
  - It reads MTL5's `mtl5_bench` results (`mtl5-bench/1` JSON plus the
    `.sysinfo` sidecar) from `benchmarks/data` into a DuckDB database. The
    database is a cache of the committed files, rebuilt with `--rebuild`.
  - **Every file is accounted for.** Each gets a row saying whether it was
    ingested, ingested as incomplete, rejected with a reason, or set aside
    (CSV for P2, reports, figures). On MTL5's current tree that is 866 files
    and 134 runs, with no rejections. 116 runs (14,196 results, 4,768
    series) have complete provenance. The other 18, from 2026-11-08 and
    -09, predate the `clock_policy` and `bench_cpus` sidecar keys.
  - **Provenance tiers.** A run with no sidecar, a missing required sidecar
    key, a dirty build, or a directory name that is not a UTC timestamp is
    ingested as `incomplete` and kept out of the `trend_results` view, as is
    any result without a passing correctness check. A run whose sidecar
    contradicts its JSON is rejected.
  - **Comparability key.** Each result has a `series_key` built from the
    physical machine, its state class (governor, turbo, power mode, clock
    policy, CPU set), the backend, the build without the commit, the thread count, the problem class, the entry and its definition
    version. Machines are fingerprinted from the hardware and host, not the
    `machine` label, which the data spells more than one way.
  - **Append-only.** Files are content-addressed, so re-ingesting an
    unchanged tree adds nothing. A changed file is a new row that supersedes
    the old one, and a deleted file gets a `removed` row. A directory that
    cannot be read aborts the ingest rather than looking like deleted files.
  - `--rebuild` deletes only a database this package wrote, and two ingests
    on one database cannot interleave.
  - New `bench` extra (`duckdb>=1.2`, `pandas>=2.0`), and CI installs it. The
    1.2 floor was tested: DuckDB 1.1.0 segfaults reopening a database the
    ingest wrote.

- **Nested dissection ordering: `ordering="nd"`** (MTL5 5.25.0, MTL5 #920).
  - It is accepted by every factorization that takes an ordering: `splu`,
    `supernodal_lu`, `cholesky`, `ldlt`, `supernodal_ldlt` and `qr`. It is
    listed in `orderings()`, and available standalone as
    `ms.nested_dissection(A)`.
  - **Measured Cholesky fill on 2-D grids, against AMD:** 1.14× at 16×16,
    1.04× at 64×64, 0.92× at 128×128 and 0.84× at 256×256. MTL5 measures
    0.64× on a 32³ grid, and its factorization work falls further.
  - The SPD guide page adds it to the fill-growth sweep. The orderings
    explainer compares it with a hand-built geometric version and with AMD.
  - **Versioning:** the MTL5 pin moves to v5.25.0, and the package version to
    5.25.0, since its MAJOR.MINOR tracks MTL5's.

- **KLU exposes its block triangular form and factors.** KLU has no single
  (L, U) pair: it factors only the diagonal blocks of B = P·(R·A)·Q and uses
  the blocks above them as they are. `ms.klu` returns that structure:
  - `row_perm`, `col_perm` and `row_scale`: P, Q and R, with
    `B == (diag(row_scale) @ A)[row_perm][:, col_perm]`;
  - `block_starts`: the block boundaries;
  - `B`: the permuted, scaled matrix, as a copy;
  - `block(i)`: diagonal block i's own `L`, `U`, `row_perm` and `col_perm`,
    with `B[s:e, s:e][row_perm][:, col_perm] == L @ U`.

  They are copies, taken under the factor's lock, so `refactor()` on another
  thread never tears them; the concurrency test now covers KLU. The orderings
  notebook shows `west0479`'s 166 blocks: 159 are 1×1, one is a 308-row core,
  and KLU stores 4,762 entries, against 6,265 for `splu` with COLAMD.

- **The pivoting factorizations' reprs show their diagnostics.**
  - `SparseLU`, `KLU` and `SupernodalLU` now print `num_perturbed` and
    `accumulator`, which were properties only. A perturbed factor is now
    visible at a glance.
  - `KLU` and `SupernodalLU` also print `nnz`, and `SupernodalLU` its
    `ordering`.
  - `SupernodalLDLT`, which printed only `n`, now prints `ordering`, `nnz` and
    `accumulator`.

  For example: `SparseLU_f64(n=479, ordering='colamd', nnz=6744,
  num_perturbed=0, accumulator='default')`. The diagnostics guide page
  documents every field.

- **The sparse direct factorizations expose their factors** (part of #125).
  Until now a factor object reported only `.nnz`, so the fill an ordering
  produced could be counted but not seen. The factors come back as
  `SparseMatrix_*` copies, so `mtl5.io.spy`, `to_scipy` and matvec work on
  them. The permutations come back as int64 arrays.
  - `splu`: `L`, `U`, `row_perm`, `col_perm`, with
    `A[row_perm][:, col_perm] == L @ U`.
  - `supernodal_lu`: the same, plus `row_scale` (None unless `scale=True`).
    The identity is then `(diag(row_scale) @ A)[row_perm][:, col_perm]`.
  - `cholesky`: `L`, `perm`, with `A[perm][:, perm] == L @ L.T`.
  - `ldlt` and `supernodal_ldlt`: `L`, `perm` and `diagonal()`. MTL5 stores
    these L without their unit diagonal; the returned L has it written out,
    so `L @ diag(D) @ L.T` reconstructs directly and `L.nnz == nnz + n`.
  - `qr`: `R`, `col_perm`. Q stays implicit as Householder vectors, so it is
    not exposed.

  The LU identities hold up to rounding only when `num_perturbed == 0`. With
  `pivot_perturb > 0`, a pivot that falls below it is replaced, so `L @ U`
  reconstructs the perturbed matrix rather than `A`.

  Two deliberate choices:
  - **Permutations use MTL5's convention, `p[new] = old`.** That is the
    inverse of scipy's `SuperLU.perm_r`/`perm_c`, so the scipy names are not
    reused for them.
  - **KLU exposes no factors.** Its block triangular form factors each
    diagonal block separately, so there is no single (L, U) pair to return.

  Each access copies O(nnz). A view would tie the Python object to a factor
  that `refactor()` overwrites in place.
- **The dense containers speak NumPy's array protocol, so scikit-learn takes
  them** (#17). Every `DenseVector_*` and `DenseMatrix_*` has an `__array__`.
  Before this, `np.asarray(mtl5.matrix(X))` was a 0-d object array, so every
  scikit-learn estimator rejected the container ("Expected 2D array, got scalar
  array"), and a vector converted only through `__getitem__`, one element at a
  time. Now:
  - **Native containers** (float, int, complex) hand NumPy a zero-copy view of
    their storage, so `np.asarray(mtl5.matrix(X))` shares memory with `X`.
  - **Universal containers** convert to float64, which is a copy, so
    `copy=False` raises `ValueError`. `.to_universal()` stays the bit-exact way
    out.
  - **Sparse matrices** get no `__array__`, deliberately: it would densify them
    silently. Pass `mtl5.sparse.to_scipy(S)` instead.
- **`tests/test_sklearn_interop.py`** covers LinearRegression, Ridge, a
  StandardScaler pipeline, `pairwise_distances`, PCA and SVC, each compared bit
  for bit with the same estimator fitted on the NumPy array. The issue listed
  PCA and SVC as expected failures because they call LAPACK. They work: LAPACK
  only ever sees float64. Two real limits are pinned instead:
  - MTL5 sparse input is rejected, as above.
  - A float32 container is computed in float64 by an estimator that takes
    either float type (Ridge). The container's `dtype` is a name (`"f32"`), not
    a NumPy dtype, so scikit-learn cannot see the float32. `np.asarray(M)`
    first is zero-copy and keeps float32.
- **`applications/sklearn_pipeline.py`**: a Ridge pipeline on features stored as
  f64, f32, posit16 and fp16, reporting what each storage format costs in test
  MSE against the noise floor.
- **CI runs the Python applications** in the `ecosystem-test` job, which has
  every optional dependency they need. No test imported them before, so they
  could break unnoticed, and one had (see Fixed).

### Fixed

- **Threshold pivoting works under a fill-reducing ordering** (MTL5 pin
  v5.24.0 → v5.24.1, MTL5 #917). `splu`, `supernodal_lu` and `klu` preferred
  the wrong row when keeping a pivot on the diagonal. Column `k` of the
  ordered matrix is `A(:, q[k])`, so its diagonal is row `q[k]`, but MTL5
  checked row `k`. As a result `threshold` barely changed fill under amd,
  colamd and rcm. On a 900-row weak-diagonal grid under AMD, `threshold=0.01`
  gave 64,118 nonzeros in L+U; with the fix it gives 21,907, and KLU goes from
  56,402 to 21,047. The default `threshold=1.0` is unchanged.
  `tests/test_sparse_direct.py::TestThresholdPivoting` pins this behaviour.

- **`refactor()` no longer races with `solve()` on another thread** (#126).
  Every sparse direct factorization releases the GIL in both `refactor()` and
  `solve()`. A `solve()` running alongside a `refactor()` of the same object
  could therefore read a factor that was halfway replaced, and return a wrong
  answer or read freed memory. A stress test with three solving threads and
  one refactoring thread saw this in every run. Each factorization now holds
  a reader/writer lock:
  - `refactor()` takes it exclusive;
  - `solve()`, `mtl5.mixed.iterative_refine` and the new factor getters take
    it shared.

  So a reader sees either the old factor or the new one, never a mix.
  Concurrent solves still run in parallel.
- **Read-only NumPy arrays are accepted wherever the input is only read or
  copied** (#116), so a pandas 3 column goes straight in:
  `mtl5.norm(df["x"].to_numpy())` used to raise `TypeError: incompatible
  function arguments`. pandas 3's copy-on-write makes `Series.to_numpy()` and
  `DataFrame.to_numpy()` read-only views, and so are `np.broadcast_to` results
  and anything with `flags.writeable = False`. nanobind admits only writable
  arrays for a non-const element type, so every array parameter refused them,
  including the `*_copy` factories, `convert`, `vector_posit16`, `norm`, `dot`,
  `solve`, `matmul`, `det`, `inv`, `lu`, `cholesky`, `mixed.*`, the sparse
  constructors and `matvec`, the sparse direct solvers' `solve`, and the
  preconditioners. They now take `const T`; the set of accepted inputs only
  grows. The Python helpers that wrapped input in a view on the way through
  (`qr`/`ldlt`/... on a NumPy array, the iterative solvers' `b`, `mtl5.io`)
  copy a read-only array instead.
- **The zero-copy views still refuse a read-only array, now with a reason.**
  `mtl5.vector`, `mtl5.matrix` and `mtl5.array.asarray` alias the array and can
  write through it, so accepting one would let MTL5 write to memory NumPy
  promised was immutable. The `TypeError` now says that and names
  `vector_copy`/`matrix_copy` or `np.array(a)`, instead of listing every
  overload's signature.
- **`Posit16Array` accepts a read-only array**, so
  `pd.array(df["col"].to_numpy(), dtype=mtl5.Posit16Dtype())` works on pandas 3.
  That broke `applications/pandas_sensor_analysis.py`. The fix is the one
  above; #115's interim copy in the constructor is gone again.

### Documentation

- **Guide page: "How fill-reducing orderings work".** It explains why the
  ordering decides the fill, and how each algorithm turns that into a rule:
  - **The elimination game.** Eliminating a vertex makes its neighbours a
    clique, and every new edge is fill. The page implements the game in a
    few lines and asserts that its count equals mtl5's Cholesky `nnz` for
    every ordering.
  - **The arrow matrix.** Hub first gives a dense factor; hub last gives no
    fill at all.
  - **Values never enter the ordering.** The same pattern with random values
    gives the same AMD ordering and the same Cholesky fill. With partial
    pivoting, values can change LU fill, and the page says so.
  - **Minimum degree and AMD.** A textbook minimum degree lands within 1% of
    mtl5's AMD.
  - **Nested dissection.** A geometric version is built by hand on grids.
    Its work grows more slowly than AMD's (n^1.62 against n^1.70), but AMD
    still wins at 2-D sizes up to 256×256, and the page says so. #138 then
    adds mtl5's own `nd` ordering to the page: its separators are smaller,
    and it beats AMD from about 100×100 up.
  - **RCM.** Its fill fills the envelope exactly on a grid.
  - **COLAMD.** The George–Ng bound is checked on `west0479`: U's pattern
    lies inside the Cholesky factor of (AQ)ᵀ(AQ) for every ordering, and the
    bound ranks the orderings the same way the actual fill does.
- **Guide page: "Diagnostics: reading a factorization"** (section 9 of #125,
  which this completes).
  - What each factor's `__repr__` shows, field by field, and what it leaves
    out: `num_perturbed`, `accumulator` and `dtype` are properties only.
  - A zero pivot raises. `pivot_perturb` lets the factorization finish and
    counts the replacements in `num_perturbed`. On a matrix with κ·u ≈ 24,
    refinement then fails to converge, and `converged=False` is how you find
    out.
  - A singular float64 matrix (the Neumann Laplacian) factors without
    raising, with `num_perturbed=0`. The pivot ratio from `ms.to_scipy(F.U).diagonal()`, or
    a small `pivot_perturb` used as a detector, catches it.
  - Threshold pivoting: from 1 to 0.001, fill falls about 3.5× while max |L|
    follows its `1/threshold` bound and the residual grows about 100×.
  - The accumulator: on a badly scaled matrix, a float64 accumulator improves
    a float32 factor's refined error 6–300×; on a well-scaled one it does
    nothing. Three combinations are refused, and the page says why.
- **Every guide page and the orderings notebook link to the API reference**
  for the functions they use, as #125's acceptance criteria ask.
- **Spy plots draw one image cell per matrix entry** (orderings notebook and
  SPD page). They used matplotlib's `ax.spy` with markers sized in points,
  and at these sizes each marker spanned 2–4 matrix rows, so neighbouring
  nonzeros merged into blobs. The pattern is now an image with one cell per
  entry, rendered at about two pixels per row. Nonzeros never overlap, and
  dense blocks still read as solid.
- **Guide page: "Mixed precision: a narrow factor, refined"** (section 7 of
  #125). A float32 Cholesky refined with `mtl5.mixed.iterative_refine`
  reaches float64 accuracy in 3 corrections on a 2-D Poisson problem, with
  half the bytes of factor values. The page also shows where it stops:
  - On this CPU the float32 factorization is not faster than the float64
    one, so the gain is memory and bandwidth, not time.
  - A conditioning sweep converges while the shift that makes the matrix
    nonsingular survives the float32 cast (κ up to about 8e6). Well past
    that, it stalls without raising. GMRES preconditioned by the same float32 factor
    converges at κ ≈ 8e8 and 8e10.
  - With data near 1e-40, the float32 corrections underflow; `scaled=True`
    recovers float64 accuracy.
  - It documents what `info["converged"]` means: with the default
    `rel_tol=0` it is always false.
- **Guide page: "A symmetric positive definite example"** (section 5 of
  #125). It factors `poisson2d` with `cholesky` and `supernodal_ldlt` under
  every ordering, and grows the grid from 16×16 to 128×128:
  - The natural ordering's fill equals the envelope of A exactly, which the
    page asserts; its growth exponent is 3/2.
  - `amd` grows like n^1.25, below `rcm` (about 1.5) and `colamd` (1.29).
    `colamd` orders AᵀA, the wrong graph for a symmetric matrix.
  - `supernodal_ldlt` stores the same pattern as `cholesky`, minus the unit
    diagonal (asserted), and is faster on the larger `amd` factors.
- **Two guide pages on the sparse direct solvers** (part of #125), executed
  at every docs build:
  - **"Sparse direct solvers"** covers sections 1–3 of #125.
    - Why use a direct solver: on `west0479`, GMRES stalls, BiCGSTAB diverges
      and ILU(0) cannot be built, while `splu` solves to rounding error. With
      20 right-hand sides, a Cholesky factor and 20 solves beat 20 CG solves
      by about 13×.
    - When not to: at the same n, a 3-D Poisson factor carries about 5× the
      fill of a 2-D one and takes about 20× longer.
    - A short cited history, from Markowitz (1957) to KLU (2010).
    - A table and decision path for choosing among the seven factorizations,
      with measured fill and timings, KLU's block structure on `west0479`,
      LDLᵀ inertia matching the eigenvalue count, and the zero-pivot case
      that only LU's pivoting handles.
  - **"Coming from SciPy"** covers section 8. It maps `scipy.sparse.linalg`

### Added

- **`universal_dtypes` arrays in and out of MTL5, bit for bit** (#14).
  `mtl5.vector()`, `mtl5.matrix()` and their `_copy` forms accept an
  `ndarray[posit16]` (and the other supported dtypes) and copy its encodings
  into the MTL5 container of the same number system. The new `.to_universal()`
  turns a container back into a `universal_dtypes` array. Neither direction
  rounds through float64, which could not carry `posit64` or a cascade's low
  limbs. `to_numpy()` still returns float64.
  - Supported: posit8/16/32/64, fixpnt8/16, lns16/32, takum32, fp16 and the
    dd/td/qd cascades. The suite checks that every 8- and 16-bit pattern, and a
    sample of the wider ones, survives the round trip and decodes the same on
    both sides. Both packages are built on Universal, but on different releases
    (4.7.9 and 5.10.0), so the name-to-format mapping is tested, not assumed.
  - Refused with `TypeError`: `fp8e5m2` (MTL5's `fp8` is a different format,
    e2m5) and the dtypes MTL5 doesn't bind (`posit12`, `q15`, `bfloat16`, …).
  - The data is copied. A view would rely on the two releases sharing a C++
    object layout, and MTL5's Universal containers have no way to keep the
    NumPy array alive.
  - `universal_dtypes` stays optional: `pip install mtl5[universal]`.
- **Integer GEMM** (#96, #88 phase 3). Two kernels, chosen by name:
  - `mtl5.mixed.matmul(A, B, accumulator="i32")` on `i8`, `i16` and `u8`
    operands, and on the mixed-signedness `u8 × i8` / `i8 × u8` pairs. It runs
    MTL5's widen-on-load `mult<int32_t>`. As for `mixed.dot`, `accumulator` is
    required on these dtypes.
  - `mtl5.mixed.matmul_quad(A, B)`, which runs `mult_quad`, the VNNI / SDOT
    micro-kernel. It takes `i8 × i8` and `u8 × i8`, which give int32, and
    `u8 × u8`, which gives uint32. It refuses `i8 × u8` with a `ValueError`,
    because a GEMM is not symmetric and cannot be reordered onto `u8 × i8`.
  - An integer matmul returns a matrix of the **accumulator's** type: `i8 @ i8`
    is a `DenseMatrix_i32`. The two kernels agree bit for bit and both equal the
    naive triple loop, because integer addition mod 2³² is associative. The suite
    asserts that exactly, on ragged shapes and across the int32 wrap.
  - `matmul` never routes through the quad kernel, and `matmul_quad` takes no
    `accumulator=`. Nothing in a result shows which kernel ran, so inferring it
    from the element types would go unnoticed. MTL5 made the same choice for the
    same reason.
- **`DenseVector_u32` / `DenseMatrix_u32`**, storage only, for the `u8 × u8`
  quad result. `mtl5.vector()` / `mtl5.matrix()` now accept `uint32` arrays,
  which used to raise `TypeError`.
- **Quad multiply-accumulate capability in `build_info()`** (#96, #88 phase 4).
  `quad_dot` is `"none"`, `"partial"` or `"all"`. `quad_dot_native` gives the
  per-pairing answer, keyed `u8xi8`, `i8xi8` and `u8xu8`. It has three states,
  not a flag, because x86 and ARM implement opposite pairings first, so
  `"partial"` is the common answer and a boolean would mislabel one pairing. A
  released wheel reports `"none"`: it is built at the x86-64 baseline.
- **`accumulator="quire"` on float32 and float64.** `mtl5.mixed.dot`, `norm`
  (ord=2) and `frobenius_norm` now accept the quire on the native dtypes, through
  Universal 5.8.0's `quire<float>` and `quire<double>` (universal#1703). Every
  product is exact and the sum is rounded once, to nearest with ties to even, so
  the result is the correctly rounded dot product. `result="element"` rounds it
  to the element type instead of to float64, which for float32 is a correctly
  rounded float32 dot product. `0 * inf` gives NaN, as IEEE 754 requires.
  `mtl5.mixed.accumulators("f32")` and `("f64")` now list `"quire"`.
  - It is slow. A quire<double> is a 4226-bit fixed-point register, and in
    mp-blas's level-3 benchmark it accumulates about 3900× slower than a
    float64 accumulator.
  - The sparse factorizations still refuse `accumulator="quire"`, now with the
    actual reason: their workspace holds one accumulator per row.

### Added

- **MTL5 pinned to v5.11.0, and `accumulator='i32'`**
  ([#88](https://github.com/stillwater-sc/mtl5-python/issues/88) phase 2). The
  narrow integer element types phase 1 registered can now compute:

  ```python
  a = np.random.randint(0, 256, 4096, dtype=np.uint8)  # activations
  w = np.random.randint(-128, 128, 4096, dtype=np.int8)  # weights
  mtl5.mixed.dot(a, w, accumulator="i32")
  ```

  MTL5 v5.11.0 routes `dot<int32_t>` over 8- and 16-bit operands onto the
  hardware widening multiply-accumulate — `vpmaddwd` / `vpdpbusd` on x86,
  `SMLAL` / `SDOT` on NEON — and an int32 accumulator is what those
  instructions accumulate into.

  **Every signedness pairing is accepted, in either order.** `u8 × i8` is VNNI's
  native shape on x86 and what quantized inference is written in; ARM implements
  the symmetric pairings first. A dot product is symmetric, so MTL5 swaps the
  operands onto whichever form the machine has. The kernel below
  (`simd::reduce_dot_widen`) rejects `(int8, uint8)`, but that restriction is the
  kernel's and re-exposing it would refuse a call the library can serve.

  **The overflow contract is part of the API, not a footnote.** Products are
  always exact; the sum wraps, and how soon depends on operand *magnitude*
  rather than vector length — roughly `2^(31-2b)` terms at `b` bits. Measured at
  full range: one `i16 × i16` product uses 2³⁰ of the int32 range, so **two**
  already overflow it, while `i8 × i8` holds **131071** terms. That five order
  of magnitude gap is why the quantized-inference instructions are 8-bit. The
  wrap is two's complement and therefore bit-identical across lane counts,
  backends and thread partitions — reproducible, but still wrapping. It is
  stated in the docstring and asserted in the tests rather than left to be
  discovered.

  Two guardrails, both deliberate. `accumulator=` is **required** for these
  dtypes, unlike every other: omitting it means element precision, which is
  exactly the wrapping phase 1 refused to expose, and silently redefining `None`
  for three dtypes alone would be worse than asking. And `result='element'` is
  **refused**, since rounding an int32 sum back to an 8-bit element
  re-introduces the wrap the accumulator exists to avoid.

  `norm` and `frobenius_norm` remain unregistered for these types: `two_norm`
  takes `sqrt` of the accumulated sum, and the API has no way to say
  "accumulate in int32, deliver a real square root".

  `mtl5.dtypes()` is deliberately **unchanged**. Its contract is the set
  `convert()` can target — the suite parametrizes over it and converts into
  every entry — and `convert()` cannot target an integer: re-quantizing reals
  into 8 bits is a quantization scheme (scale, zero point, rounding mode), not
  a cast, and a naive version would silently clip everything outside
  [-128, 127]. `mtl5.mixed.accumulators('i8')` answers for them instead.

  The v5.11.0 pin is what makes this sound rather than merely available.
  `batch<int32_t>` does not exist before it, so the kernels are absent — and
  `detail/wrapping_arithmetic.hpp` is new in it, without which the generic
  integer loops are **UB** on overflow rather than the documented modular wrap.
  For these operand widths overflow is the normal regime, not an edge case.


### Added

- **Narrow integer element types: `i8`, `i16`, `u8`**
  ([#88](https://github.com/stillwater-sc/mtl5-python/issues/88) phase 1).
  These are the operand types of MTL5 v5.11.0's widening dot and integer GEMM —
  the accumulator stays `int32`, which is what `vpdpbusd` / `vpmaddwd` / `SDOT`
  take — so registering the containers is what makes those kernels reachable at
  all. **Those kernels arrive with the v5.11.0 pin; this phase does not require
  it** and is built and tested against the current v5.10.0.
  `mtl5.vector(np.arange(4, dtype=np.int8))` now gives a
  `DenseVector_i8`, zero-copy, alongside `DenseMatrix_i8` and the `u8`/`i16`
  equivalents.

  **This also fixes a silent wrong-dtype bug.** The native factories take
  `nb::ndarray<T>` without `.noconvert()`, so nanobind's converting second pass
  handed an int8 array to the *float* overload — registered first — and
  `mtl5.vector(int8_array)` returned a `DenseVector_f32` that reported
  `is_view=True` while being a view of the converted temporary, so writes
  through the NumPy array were invisible. An exact match now resolves in the
  first pass, before conversion is considered. The dtypes that remain
  unregistered (`f16`, `uint16`, `uint32`, `uint64`) still behave the old way.

  **`dot`, `norm` and `__matmul__` are deliberately not registered for these
  types**, and that is a measurement rather than caution. All three default to
  accumulating in the element type, so on 8- and 16-bit operands they overflow
  almost immediately. One input covers all three, since each sums the same six
  products — vectors of six 100s, and a 6×6 of 100s. Exact `dot` and exact
  `A @ A` element are both 60000; exact `two_norm` is 244.9490:

  | | `i8` | `i16` | `u8` |
  |---|---|---|---|
  | `dot` | 96 | −5536 | 96 |
  | `two_norm` | 9.798 | **nan** | 9.798 |
  | `A @ A` | 96 | −5536 | 96 |

  `two_norm` is `sqrt(dot)`, which is what makes the `i16` nan legible: the sum
  wrapped negative, and `sqrt(-5536)` has no answer to give.

  These are MTL5's documented two's-complement wrapping and become correct the
  moment an int32 accumulator is supplied. `i16` has real headroom — a 2×2 of
  100s gives the exact 20000 — so its failure needs a longer `k` rather than
  being immediate; that is a difference of degree, since `k=4` already wraps it
  and nothing in the API tells a caller where the edge is. `i32` has the same
  failure past ~46341, where an 8-bit sum of squares overflows at two elements
  of 12 — an edge case there, essentially every input here.

  `mtl5.dot(i8_vec, i8_vec)` and `i8_mat @ i8_mat` therefore raise `TypeError`
  rather than returning a wrapped number, until phase 2 lands the accumulator.
  `__matmul__` is registered on the matrix class itself, so this needed
  `register_native_matrix` split from `register_native_matrix_matmul` — the
  existing types are registered exactly as before.


- **nanobind 3 is supported**, and the build requirement widens from
  `nanobind>=2.0,<3` to `>=2.0,<4`
  ([#85](https://github.com/stillwater-sc/mtl5-python/issues/85)). The cap added
  when nanobind 3.0.0 broke every wheel build was a hold, not a fix; this is the
  port. **Both majors are built and tested** — 1374 passed, 3 skipped under each
  of nanobind 2.15.0 and 3.0.0.

  nanobind 3 removed the free `nb::detail::keep_alive(nurse, patient)`, routing
  the same operation through a backend slot that must be handed the extension's
  context pointer. `mtl5_ndarray.cpp` now spells it once, in `keep_view_alive()`,
  which selects the form on `NB_VERSION_MAJOR` — so the bound moved rather than
  jumped, and a source build against either major produces the same behaviour.

  The obvious simplification is wrong, and there is now a test saying so.
  Replacing these calls with the declarative `nb::keep_alive<0, 1>` annotation
  would compile and pass the old suite, but the annotation applies to **every**
  return of a `.def`, and `__getitem__`, `reshape` and `ravel` each return a
  view on one path and a copy (or, for a fully-integer index, a scalar) on
  another. Pinning a large source array to an independent copy of itself is a
  memory-retention bug, so the pin has to stay per-path.

  Two gaps in the lifetime tests are closed as part of this, both of which a
  broken keep-alive would previously have survived:
  - `test_a_view_of_an_OWNING_array_keeps_it_alive` — the existing test derives
    its views from `asarray()`, where the view *also* carries the NumPy owner
    object, so the buffer survives on that reference alone. A `copy()` owns its
    memory with no second owner, which is the configuration where dropping the
    parent is a genuine use-after-free.
  - `test_a_copy_does_not_pin_its_source` — asserts the aliasing/copying split
    directly, via refcount: a view increfs its parent, a copy does not.

### Fixed

- **`vector()` and `matrix()` no longer silently convert their input.** All
  eight factory overloads (native and complex, view and copy) take
  `.noconvert()`, so the dtype must match a registered one exactly and the
  array must be C-contiguous.

  The reported symptom was unregistered dtypes — `f16`, `uint16`, `uint32`,
  `uint64` — coming back as `DenseVector_f32`. Fixing it turned up something
  worse, because nanobind's converting pass repacks **layout and dtype
  together** and takes the first overload that converts, which is `float32`:

  ```python
  a = np.array([0.1, 1.0, 0.2, 2.0, 0.3, 3.0])  # float64
  v = mtl5.vector(a[::2])
  # v is a DenseVector_f32, v.is_view is True, and v[0] == 0.10000000149011612
  ```

  An ordinary float64 slice was **silently downcast to float32** while
  reporting `is_view=True` and aliasing nothing. The old test covering this
  used values (1.0, 3.0, 5.0) that are exact in float32, which is why it read
  as benign.

  Both now raise `TypeError`, listing every accepted dtype. `np.ascontiguousarray(a)`
  is the deliberate way to ask for the copy, and it keeps float64. This matches
  what `mtl5.array.asarray` has always done — its `.noconvert()` carries the
  same reasoning, and the factories simply never got it.

  **This is a behaviour change.** Code passing a non-contiguous array, or a
  dtype outside {f32, f64, i8, i16, i32, i64, u8, c64, c128}, now raises where
  it used to return a quietly converted result.

### Added

- **`mtl5.system_info()`**, and **`build_isa`** in `build_info()` (MTL5
  [#443](https://github.com/stillwater-sc/mtl5/issues/443)). `build_isa` is the
  SIMD ISA the binary was *compiled for*, read from the compiler's own
  predefined macros; `system_info()["cpu_simd"]` is what the machine *supports*.
  Only the first explains a throughput number, and until now nothing in the
  Python surface reported it: `highway_simd: True` says the micro-kernel
  vectorised, not how wide, and Highway's static dispatch fixes that at compile
  time. On a wheel built the way CI builds them this reads `SSE2` against a
  machine's `SSE2 AVX AVX2 FMA` — which is correct and intended, and now
  visible rather than inferred. `system_info()` additionally reports CPU brand,
  vendor, arch, logical cores, OS, compiler, `__cplusplus` and `Release`/`Debug`.

  MTL5's sibling `<mtl/build_info.hpp>` (its git commit / dirty flag / configured
  `cxx_flags`) is deliberately not used: it is CMake-generated into MTL5's binary
  directory and is absent from MTL5's `install()` list, so depending on it would
  compile under FetchContent and fail against an installed MTL5. Its one field
  worth having here, `Release` vs `Debug`, comes from `compiler_info::build_type`
  instead.

- **A regression guard on the benchmark numbers**
  ([#73](https://github.com/stillwater-sc/mtl5-python/issues/73) item 3, the
  last one). The harness emitted JSON with build flags, thread count and
  platform precisely so results could be tracked, and nothing consumed it: a
  change that made posit32 GEMM 3x slower would not have been noticed.

  Guarding timings is an easy way to build a flaky test, so both *what* is
  asserted and *which kernel* it is asserted on were chosen from measured
  stability. Four runs per configuration, ratios taken within each run:

  | kernel | ratio | spread |
  |---|---|---|
  | `gemm` n=64 | posit32/takum32 | **1.04x** |
  | `gemm` n=64 | posit32/f64 | **1.03x** |
  | `gemv` n=256 | posit32/takum32 | 1.42x |
  | `dot` n=10000 | posit32/takum32 | 3.29x |

  **Only `gemm` is guarded.** `dot` and `gemv` were tried and rejected on those
  numbers — a guard that swings 3x between identical runs cannot distinguish a
  regression from a Tuesday. `dot` stays unstable even at n=10000, where the
  operands are far above per-call overhead, and even with best-of-3, so the
  instability is not something a larger size fixes.

  Ratios are taken *within* a run, which cancels machine speed and scheduler
  noise almost exactly and is what lets order-of-magnitude bounds hold on an
  ordinary shared runner. The guards catch a structural regression — a
  vectoriser silently off, an emulated path falling back, a format losing its
  fast route — and were verified to fire by injecting each of those, rather
  than merely observed to pass.

  Marked `perf`, so `pytest -m "not perf"` skips it where timing is meaningless.
  Costs about six seconds.

- **`--accumulators` on the BLAS benchmark: what does exactness cost?**
  ([#73](https://github.com/stillwater-sc/mtl5-python/issues/73) item 2.)
  `dot`, `gemv` and `gemm` take an `accumulator=` argument — the precision the
  sum is carried in, independent of the element type — and its price had never
  been measured. The new axis reports each accumulator against **the same
  dtype's default**, not against float64, because the question is what
  exactness costs for a given format rather than how slow that format is.

  **There is no single answer — the quire's cost spans a factor of 40 across
  formats.** On one recorded run (x86_64, single thread, `dot`), against each
  dtype's own default accumulator:

  | dtype | quire | `f64` accumulator |
  |---|---:|---:|
  | `posit32` | **0.86x** | 0.35x |
  | `fixpnt16` | 1.66x | — |
  | `cfloat32` | 3.02x | 0.50x |
  | `lns32` | **36.7x** | 0.93x |

  So for the posit family exactness is free — slightly *cheaper* than
  accumulating in the element type, because posit addition is expensive to
  emulate while a quire accumulate is fixed-point. For `lns32` it is
  prohibitive: logarithmic multiplication is cheap, but every term has to leave
  the log domain to reach a fixed-point accumulator. Anyone budgeting an
  experiment on "the quire costs about X" would be wrong for three of these
  four formats, which is the point of being able to measure it.

  A second result falls out: accumulating in `f64` is consistently *cheaper*
  than accumulating in the emulated element type (0.35x-0.93x), since a native
  double add costs almost nothing next to an emulated one.

  Accuracy was verified rather than assumed — a faster quire that had quietly
  stopped accumulating exactly would look like a win. Against an exact rational
  reference over the rounded operands, 4000 `posit32` terms: the quire is
  correctly rounded at 1.3e-16 while the element default carries 9.2e-07, seven
  orders of magnitude worse.

  Availability is read from `mtl5.mixed.accumulators()` rather than hardcoded,
  so only the four families Universal ships an `fdp.hpp` for are swept for a
  quire; `takum32` and the cascades are skipped instead of filling the table
  with rejections. `lu`/`qr` have no accumulator parameter and are not swept.
  Native `f32`/`f64` `gemv`/`gemm` report the gap honestly: the top-level
  `mtl5.matvec`/`matmul` take no accumulator, only the `mixed.*` entry points
  do.

- **Every dense factorization now covers every Universal number system.**
  `lq`, `cholesky`, `ldlt` and `bunch_kaufman` join `lu` and `qr`, so all six
  are available for float32, float64 and all fifteen Universal dtypes
  ([#73](https://github.com/stillwater-sc/mtl5-python/issues/73)).

  Two separate gaps, one cause. `cholesky` and `ldlt` kept hand-copied
  instantiation lists that stopped at `lns32`, so they missed the five types
  added in #70; `lq` and `bunch_kaufman` were never extended past
  float32/float64 at all. Every factorization now routes through the single
  `for_each_universal<>` list added in #71, so adding a number type is one line
  and coverage cannot drift again — asserted directly by a test that compares
  the six coverage sets and fails on any difference.

  Nothing upstream had to change: all four compile for all fifteen types.
  Bunch-Kaufman's 1x1/2x2 block pivoting is comparisons and arithmetic, so no
  number system has to opt in.

  **Availability is not usability, and the two diverge sharply.** The
  orthogonalizing pair fails first — `lq` inherits `qr`'s degeneracy exactly,
  with `fp8` and `fixpnt8` returning `Q == I` while looking perfect. The
  solving three have no orthogonality to lose and stay usable to 8 bits, the
  worst measured residual being ~6e-2. One divergence is worth knowing:
  `fixpnt16` is fine for `qr` and saturates for `lq` at the same width, because
  LQ works along rows and on this fixture that order drives an intermediate
  past `fixpnt<16,8>`'s limit of 128.

- **`lu()` and `qr()` for every Universal number system.** Both were
  float32/float64 only, which was the last prerequisite in
  [#69](https://github.com/stillwater-sc/mtl5-python/issues/69) — the
  number-system benchmark could report `dot`/`gemv`/`gemm` for the emulated
  formats but had a hole where the two factorizations should be. Householder QR
  and partial-pivoting LU need only `sqrt` and the arithmetic operators, so all
  fifteen bound types compile; no upstream change was needed.

  LU is exposed as a reusable factorization object, not just through the
  existing `solve()`, which threw the factorization away on every call. Factor
  once at O(n³), solve many right-hand sides at O(n²) — and it is what the
  benchmark can now time without conflating the factorization with the
  triangular solves.

  Unlike `gemv`/`gemm`, these two run the **same** kernel for native and
  emulated types, so their ratios are a like-for-like comparison rather than one
  that partly measures the vectoriser. On one recorded run (x86_64, single
  thread), QR at n=64 cost `takum32` ~169x double, `cfloat32` ~272x,
  `dd_cascade` ~348x, `lns32` ~930x and `posit32` ~1905x.

  **Two formats fail silently and that is worth knowing before trusting a
  number.** For `fp8` and `fixpnt8`, every Householder reflector rounds to zero
  (measured: `sum|tau| == 0` exactly), so `.Q` is returned as the exact identity
  and `.R` as the upper triangle of A. The factorization then scores a perfect
  `||QᵀQ − I|| == 0` while its product reconstructs only `triu(A)` — the
  residual is exactly the weight of the discarded subdiagonal, so it is a
  property of the input, not a fixed figure for the format (9% to 45% across
  the matrices tried). It looks flawless and is meaningless. It does not raise, because a genuinely upper-triangular input
  has zero reflectors too and that case is correct. `posit8` is unusable by a
  different route — its reflectors do not vanish, it is simply inaccurate
  (residual 0.47, orthogonality 1.3). All three are registered anyway: comparing
  number systems is the point, and a format failing is a result.
  `tests/test_universal_factorizations.py` pins where each tier stops.

  `lq` remains float32/float64 only and is unchanged.

- **Five number types — `cfloat32`, `takum32`, `dd_cascade`, `td_cascade`,
  `qd_cascade` — across `convert()`, the containers, and the mixed-precision
  `dot`/`gemv`/`gemm`.** All five already existed in Universal v4.7.9, the
  version already pinned, so this is binding work only: aliases, `type_suffix`,
  and the instantiation lists.

  `cfloat32` earns its place by being redundant on paper. It is IEEE binary32
  semantics through the same emulation layer everything else uses, so pairing
  it against hardware `float` separates *emulation overhead* from *format
  cost* — without it, a posit32-vs-double ratio conflates the two and cannot
  say which one to attack. Measured, that distinction is the whole story: on
  one recorded run (x86_64, single thread, `native_fast_gemm` + `highway_simd`,
  no `-march=native`), GEMM at n=64 cost `cfloat32` ~570x double and `posit32`
  ~4000x, so most of posit32's cost is posit-specific rather than the price of
  emulation. Those figures are an example from one host, not a portable
  constant — the ratios move with build flags, ISA dispatch, thread count and
  architecture, which is why the harness records all four alongside them.

  `accumulator='quire'` works for `cfloat32` and is *rejected* for `takum32`
  and the cascades. Quire availability follows Universal's `fdp.hpp`, not our
  type list, and a silent fallback to a lesser accumulator would quietly
  invalidate an exactness claim — so it raises, as it already does for native
  `float`.

  The cascades' extra precision is invisible at the Python boundary by
  construction: `convert()` takes float64 in and `to_numpy()` hands float64
  back. What they buy is intermediate accumulation, which is why their test
  asserts on a catastrophically cancelling sum rather than on a round trip.

- **`benchmarks/bench_blas.py`** — BLAS throughput as a function of number
  type, reporting slowdown against float64 rather than raw GFLOP/s, because
  experiment planning is built out of "posit32 GEMM costs 4000x double".

  It reports a structural asymmetry instead of hiding it: the native baselines
  run MTL5's blocked Highway-vectorised kernels while the emulated types run
  the generic ones, so part of every `gemv`/`gemm` gap is the vectoriser rather
  than the number system. `lu` and `qr` have no such split — both sides run the
  same kernel — so those ratios are like-for-like.

  (As first written, the harness also reported `lu`/`qr` as `not instantiated`
  for every emulated type, which was true when it was added and stopped being
  true later in the same release cycle. The `unavailable` status remains, since
  it is the honest way to report a gap and is what keeps a sweep from aborting
  on the first one.)

  It also measures each kernel's own call floor and flags baselines that sit
  within 20x of it. Small-`n` rows are otherwise quietly misleading: an f64 dot
  at n=64 is mostly binding overhead, which inflates the baseline and
  *understates* every ratio computed against it.

  reframing is conditional on the error mentioning `_core`: an unrelated
  `ImportError` — a missing dependency inside `tensor.py`, say — still surfaces
  as itself rather than sending someone off to rebuild a C++ extension for no
  reason.

  Both directions are tested, in subprocesses, against the real extension.

- **The accumulator tests ranked accumulators against a float64 reference, so
  they penalised the quire for being exact.** Tests only — no shipped code
  changed, and the binding behaviour was always correct. The reference was
  `np.dot`, which is itself a float64 accumulation carrying its own rounding
  error — and whose summation order is not even fixed, since it dispatches to
  whatever BLAS numpy was built against — so
  `test_wider_accumulator_is_monotonically_better` was
  really measuring *agreement with float64*: the `f64` accumulator reproduced
  the reference bit for bit and scored a perfect `0.0`, while the exact quire
  differed from it by `1.14e-16` and therefore scored worse, failing the
  `quire <= f64` assertion. Not a flake — it fails whenever the `f64`
  accumulator matches numpy's summation order, which is the ordinary case; CI
  stayed green only because FP contraction on those runners perturbed one of
  the two.

  The reference is now `math.fsum`, which tracks exact partial sums and is
  therefore correctly rounded independently of summation order. (CPython
  documents one residual caveat: on builds whose C library adds in extended
  precision, an intermediate sum can double-round and leave the result off by
  one ulp. Not observed on any platform in CI.) The quire reproduced it
  bit-for-bit for both `dot` and `two_norm` on every lane — an observed result
  across Linux, macOS/arm64 and Windows, not a guarantee derived from the
  standard. That let the tests assert the real property
  instead of a tolerance: `test_quire_is_exact_for_posit` now asserts exact
  equality rather than `rel=1e-15` — the old tolerance was absorbing the same
  discrepancy, so the headline "the quire is exact" claim was never actually
  being tested — and the ordering test asserts `quire == 0.0`, which `quire <=
  f64` follows from and which is not satisfied by a quire that merely ties.

  The same defect in `test_a_wider_accumulator_is_strictly_better` is fixed
  too. It referenced `np.longdouble`, which is 80-bit only on x86 Linux and
  plain float64 on Windows and macOS/arm64 — so on two of the three CI
  platforms its `err["quire"] == 0.0` assertion was already being made against
  a float64 reference and passing on luck.
  ([#62](https://github.com/stillwater-sc/mtl5-python/issues/62),
  [#63](https://github.com/stillwater-sc/mtl5-python/pull/63))

## [5.9.0] - 2026-08-10

Tracks MTL5 **v5.9.0**. No Python API change — the minor bump is the version
policy (minor follows the MTL5 release built against), not new surface.

### Changed

- **MTL5 and Universal are pinned to release tags, not `main`.** Both were
  fetched from `main`, and FetchContent runs at `pip install` time — so every
  wheel CI shipped, and every from-source install, was built against whatever
  those branches happened to be at that moment. 5.7.0 through 5.7.2 are not
  reproducible for that reason. They are now `mtl5 v5.9.0` and
  `universal v4.7.9`, and bumping the MTL5 pin is what a minor release of this
  package now means.

  v5.9.0 is a floor rather than a preference: the bindings do not compile
  against MTL5 v5.8.0. `mtl5_mixed_precision.cpp` calls the
  `two_norm<Accumulator, Result>` / `frobenius_norm<Accumulator, Result>`
  forms, and v5.8.0's signature is `template <typename Accumulator = void,
  Vector V>` with no `Result` parameter; `mtl5_complex.cpp` calls the Hermitian
  factorizations `cholesky_h_factor` / `cholesky_h_solve` / `ldlt_h_factor` /
  `ldlt_h_solve` and `CHOLESKY_NOT_HERMITIAN`. Both arrived after v5.8.0, so
  there is no v5.8.0-backed release of this binding surface.

  The floor is enforced on **both** build paths. A bare `find_package(MTL5
  QUIET)` accepts any system-installed MTL5 and skips the pinned fetch
  entirely, so the pin governed only one of the two ways this package gets
  built; a developer with 5.7.x installed would have built against it silently
  and hit ~140 template errors inside `norms.hpp` rather than a version
  message. Both lookups are now version-floored
  (`find_package(MTL5 5.9.0 QUIET)`, `find_package(universal 4.7.9 QUIET)`).
  Under `COMPATIBILITY SameMajorVersion` — which both projects generate — that
  rejects an installed 5.7.0, accepts 5.9.0 and 5.10.0, and rejects 6.x, the
  last being correct in its own right: an MTL5 major bump is the
  manual-intervention case in the version policy, not something to absorb
  silently. ([#61](https://github.com/stillwater-sc/mtl5-python/pull/61))

- **Release pipeline consolidated into one workflow.** `release.yml` plus a
  reusable `wheels.yml` were merged into a single `wheels.yml` with three
  triggers: `push: main` (semantic-release cuts the version, then builds and
  publishes in the same run), `release: published` (manual), and
  `workflow_dispatch` (TestPyPI dry-run). PyPI Trusted Publishing does not
  support reusable workflows, and a `GITHUB_TOKEN`-created release does not
  cascade to another workflow — so build+publish now run as native jobs
  alongside semantic-release: keyless OIDC, a single trusted-publisher
  registration per index (no separate `release.yml` publisher needed), and
  least-privilege per-job permissions. No runtime or API change.
  ([#57](https://github.com/stillwater-sc/mtl5-python/pull/57))

## [5.7.0] - 2026-08-07

First release to PyPI. Closes epic #21 — the binding gap against MTL5 v5.7.0.
Every module the 2026-08-01 gap analysis inventoried is now reachable from
Python, taking the surface from roughly 14 numerical entry points to over 150.

### Added

- **Mixed precision** — `accumulator=` on `dot`, `norm`, `frobenius_norm`,
  `matvec` and `matmul`; `convert`, `lu_iterative_refine`, `backward_error` and
  sparse `iterative_refine`. Accumulating 4000 posit16 products is bit-exact
  with the quire against 1.8 × 10⁻¹ unaccumulated.
- **Sparse direct solvers** — `splu`, `klu`, `cholesky`, `ldlt`, `qr`,
  `supernodal_lu`, `supernodal_ldlt`, with the analyze/factor/refactor split,
  plus AMD/COLAMD/RCM orderings.
- **Accumulator policy on the sparse factorizations** — a float32 factor can
  accumulate its updates in float64. Paired with iterative refinement on an
  ill-conditioned matrix: 4 iterations to 1.4 × 10⁻¹⁰ instead of 6 to
  2.0 × 10⁻⁹.
- **Dense completeness** — QR, LQ, LDLᵀ, Bunch–Kaufman; the eigen and SVD
  family; BLAS level 2/3; 28 property predicates.
- **Complex element types** — `c64`/`c128` containers, norms, Hermitian `dot`
  and `dot_real`, products, `solve`/`lu`/`inv`, `transpose`/`adjoint`/`conj`,
  QR/LQ with least squares, Hermitian Cholesky, and `ldlt_solve` dispatching
  between LDLᵀ and LDLᴴ.
- **Sparse storage formats** — COO and ELL alongside CSR, with `padding_ratio`
  to decide whether ELL fits, and a native transpose-SpMV so a SciPy
  `LinearOperator` no longer round-trips through scipy.
- **N-dimensional arrays** (`mtl5.array`) — ranks 1–4, zero-copy in both
  directions with strides, slicing, reductions, and interop with the dense
  containers.
- **Krylov solvers and preconditioners** — 10 solvers and 8 preconditioners in
  any combination, via a type-erased preconditioner: 20 template instantiations
  rather than the 160 the cross product would have cost.
- **Smoothers and multigrid** (`mtl5.mg`) — seven smoothers, grid transfer, a
  sparse `galerkin` product, and a hierarchy builder. About 0.03 residual
  reduction per V-cycle on 1-D Poisson, holding as the problem grows.
- **Matrix views** (`mtl5.view`) — eight views, materialised rather than
  aliasing.
- **Tensor algebra** (`mtl5.tensor`) — fixed-dimension containers, Einstein
  contraction with runtime index strings, outer products, metric raise/lower,
  packed symmetric storage.
- **Test matrices, I/O and build** — 25 generators with prescribed spectra,
  Matrix Market read/write, `spy` PNGs with no plotting stack, and all five
  MTL5 acceleration options wired through.

### Changed

- `mtl5.sparse.cg`, `gmres` and `bicgstab` keep their signatures and gain a
  working `M=`, which previously raised `NotImplementedError` and pointed at
  scipy.
- The accumulated norms now call `mtl::two_norm<Acc, Result>` directly. They
  went through local sum-of-squares loops until upstream added the `Result`
  parameter, without which `accumulator=` was unobservable from Python.

### Fixed

Seven defects were found in MTL5 and reported; all seven were fixed upstream and
the workarounds retired. Six returned a wrong answer while reporting success:

| upstream | defect |
|---|---|
| [#352](https://github.com/stillwater-sc/mtl5/issues/352) | `ldlt` gave a wrong solution for a Hermitian complex matrix with `info = 0` |
| [#353](https://github.com/stillwater-sc/mtl5/issues/353) | complex `cholesky` and `qr` did not compile |
| [#355](https://github.com/stillwater-sc/mtl5/issues/355) | `compressed2D` accepted `tag::col_major` and ignored it, transposing CSC input |
| [#359](https://github.com/stillwater-sc/mtl5/issues/359) | `ndarray` reshape and flatten returned memory order for F-contiguous input |
| [#379](https://github.com/stillwater-sc/mtl5/issues/379) | the norms had no `Result` parameter, so the accumulator was unobservable |
| [#392](https://github.com/stillwater-sc/mtl5/issues/392) | `bicg` computed `rho` from the wrong vectors and worked only unpreconditioned |
| [#401](https://github.com/stillwater-sc/mtl5/issues/401) | `mg/multigrid.hpp` was not self-contained |

### Notes for callers

Some inputs are refused that a caller might expect to work. Each is deliberate
and load-bearing:

- `bicg` and `qmr` refuse a non-symmetric preconditioner. They are the only
  solvers applying Mᵀ, and MTL5 implements a preconditioner's adjoint as its
  forward solve — exact when M is symmetric, a breakdown otherwise.
- `refactor()` on `splu`, `klu` and `supernodal_lu` refuses when a non-default
  accumulator is in effect, rather than silently reverting to element precision.
- `mtl5.view.banded` refuses a negative bandwidth (the parameters are counts,
  not signed diagonal offsets) and `mtl5.view.hermitian` a non-real diagonal.
- `mtl5.array.asarray` requires an exact dtype match; converting would return a
  view of a temporary, which is neither zero-copy nor the dtype requested.
- There is no CSC. MTL5 has no column-major sparse container, so `from_scipy`
  converts at the boundary.

Two operations differ from NumPy on purpose: `dot` on complex is Hermitian
(`numpy.vdot`, not `numpy.dot` — `dot_real` is the latter), and `.T` does not
conjugate, `.H` does.
